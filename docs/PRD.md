# ODOQ — One Day One Quote (기획 초안 v0.1)

> 하루에 한 문장. 오늘의 한마디를 남기고, 남의 한마디를 읽는다.

작성일: 2026-09-12 / 상태: 초안(미확정 항목은 §10 참조)

---

## 1. 제품 정의

| 항목 | 내용 |
|---|---|
| 한 줄 정의 | 하루 1회, 최대 N자의 짧은 글을 남기는 미니 다이어리 + 소셜 피드 |
| 핵심 행동 | 쓴다(1일 1회) → 읽는다(팔로잉/전체) → 팔로우한다 |
| 차별점(가설) | "하루 1개" 제약이 부담을 낮추고(빈 페이지 공포 제거) 매일 열 이유를 만든다 |
| 성공 기준(MVP) | D7 리텐션 25%, 가입자당 주 4회 이상 작성, 작성자 중 30%가 1인 이상 팔로우 |

### 핵심 가설과 반대 근거 (확인 전 가정)

| 가설 | 반대 근거 / 리스크 |
|---|---|
| 제약(1일 1개)이 리텐션을 만든다 | 쓸 말이 없는 날 = 이탈일. 하루 놓치면 "스트릭 깨짐"으로 영구 이탈 가능 → 스트릭을 벌칙이 아닌 누적 지표로 설계 |
| 남의 글을 보는 게 재미다 | 콜드스타트에 콘텐츠가 없으면 빈 피드. 초기 100~300개 시드 콘텐츠/에디터 큐레이션 필요 |
| 팔로우가 관계를 만든다 | 초기 유저는 팔로우할 대상이 없음 → 팔로우 탭보다 **발견(전체) 탭이 기본**이어야 함 |
| 짧은 글이라 관리가 쉽다 | UGC는 무조건 신고·차단·삭제가 필요. 없으면 App Store 심사 리젝(Guideline 1.2 UGC) |

## 2. 타깃

- 1차: 일기 앱을 세 번 시도하고 세 번 실패한 20~30대 (부담 없는 기록 욕구)
- 2차: 문장·글귀 수집형 사용자 (인스타 "글스타그램" 소비층)
- 비타깃: 장문 일기, 사진 중심 기록, 비공개 전용 저널 (→ 기존 앱이 더 잘함)

## 3. MVP 범위

### In scope

| # | 기능 | 설명 |
|---|---|---|
| F1 | 계정 | 소셜 로그인(Apple/Google) + 닉네임·핸들 설정 |
| F2 | 오늘의 한마디 작성 | 1일 1개, 최대 140자, 공개/비공개 선택 |
| F3 | 수정/삭제 | 작성 당일에 한해 수정 가능, 삭제는 언제나 가능 |
| F4 | 내 기록 | 캘린더/리스트로 과거 글 열람 (내 아카이브) |
| F5 | 피드 | 전체(발견) 탭 + 팔로잉 탭 |
| F6 | 팔로우 | 팔로우/언팔로우, 팔로워·팔로잉 목록 |
| F7 | 프로필 | 타인 프로필에서 공개 글만 열람 |
| F8 | 반응 | "공감" 1종만 (좋아요). 댓글 없음 |
| F9 | 안전 | 신고, 차단, 계정 삭제 |
| F10 | 알림 | 작성 리마인더(1일 1회, 시간 설정), 팔로우/공감 알림 |

### Out of scope (v1 이후)

댓글, DM, 해시태그/검색, 이미지 첨부, 공유 카드 이미지 생성, 웹 버전, 다국어, 프리미엄 결제.

> 판단: **댓글은 v1에서 제외**가 맞다. 짧은 글 + 댓글은 갈등 비용이 크고 모더레이션 부담이 커진다. 공감 1종으로 시작해 반응 데이터를 본 뒤 결정.

## 4. 핵심 정책 (제품의 성격을 결정하는 규칙)

| 정책 | 초안 | 근거 / 대안 |
|---|---|---|
| 작성 횟수 | 1일 1개 (사용자 로컬 타임존 기준 00:00 리셋) | 앱 이름과 직결. 대안: 1일 1개 + "덮어쓰기 허용" |
| 글자 수 | 140자 | 한국어 140자면 2~3문장. 대안: 100자(더 강한 제약) |
| 수정 | 당일만 허용 | 과거 조작 방지 + 기록물 신뢰성 |
| 공개 범위 | 글 단위 public/private | 비공개 글은 피드·프로필 어디에도 노출 안 됨 |
| 피드 정렬 | 전체 탭: 최신순(24시간 내) / 팔로잉 탭: 최신순 | 알고리즘 랭킹은 데이터 쌓인 후. 초기에 인기순은 소수 독식 유발 |
| 열람 조건 | 제한 없음(자유 열람) | 대안: "오늘 글을 써야 오늘 피드가 열린다" — 리텐션엔 강력하나 신규 이탈 위험. **A/B 후보** |
| 팔로우 승인 | 불필요(공개 팔로우) | 비공개 계정은 v1.1 |

## 5. 화면 구조 (IA)

```
[탭바]
├─ 오늘      : 오늘 글 작성 / 작성 완료 시 내 글 + 스트릭
├─ 피드      : [전체] [팔로잉] 세그먼트
├─ 기록      : 캘린더 + 리스트 (내 아카이브)
└─ 프로필    : 내 프로필 / 설정

[스택]
- 글 상세 (공감, 신고, 작성자 프로필 이동)
- 타인 프로필 (공개 글 목록, 팔로우 버튼)
- 팔로워 / 팔로잉 목록
- 설정 (알림 시간, 차단 목록, 계정 삭제, 약관)
- 온보딩 (로그인 → 핸들 설정 → 알림 권한 → 첫 글 작성)
```

## 7. 기술 스택 (제안)

| 레이어 | 선택 | 근거 |
|---|---|---|
| 앱 | React Native + Expo (SDK 최신) | iOS/Android 동시, OTA 업데이트, 푸시 내장. 기존 `ktwbank` 레포는 bare RN이지만 신규는 Expo가 운영비 절감 |
| 상태/데이터 | TanStack Query + Zustand | 서버 상태와 UI 상태 분리 |
| 백엔드 | Supabase (Postgres + Auth + RLS + Storage) | 팔로우·피드 쿼리가 관계형에 적합. RLS로 공개/비공개 강제 |
| 푸시 | Expo Push Notifications | 리마인더/팔로우 알림 |
| 분석 | PostHog 또는 Amplitude | 퍼널·리텐션 필수 |

> 리스크: Supabase RLS만으로 피드 성능이 안 나오는 시점(팔로잉 수천 명 이상)이 온다. 그때 피드 캐시 테이블 또는 별도 API 레이어 도입. MVP 규모에선 문제되지 않음(가정).

## 9. 마일스톤 (초안, 1인 개발 기준 추정)

| 단계 | 범위 | 기간(추정) |
|---|---|---|
| M0 | 스키마·RLS·인증 + 온보딩 | 1주 |
| M1 | 작성/수정/삭제 + 내 기록 (로컬 완결형 다이어리로도 동작) | 1.5주 |
| M2 | 피드(전체/팔로잉) + 프로필 + 팔로우 | 2주 |
| M3 | 공감 + 알림 + 신고/차단 | 1.5주 |
| M4 | 시드 콘텐츠, 스토어 심사 대응, 클로즈드 베타 | 1주 |

합계 약 7주. **M1까지만으로도 단독 출시 가능한 형태**로 자른 것이 핵심(소셜 없이도 앱이 성립).

## 10. 미결정 사항 (진행 전 결정 필요)

1. **열람 조건** — 오늘 글을 써야 피드가 열리는가? (리텐션 ↑ / 신규 이탈 ↑)
2. **실명성** — 핸들 기반 준익명인가, 지인 기반인가? 지인 기반이면 연락처 동기화가 필요하고 심리적 부담이 커짐
3. **글자 수** — 100 / 140 / 200
4. **댓글 부재** 확정 여부
5. **수익 모델** — v1 없음 전제. 이후 테마·아카이브 내보내기·광고 중 무엇?
6. 서비스명/도메인/스토어명 확정 (`ODOQ` vs `One Day One Quote`)
